ReviewHive

完全运行于本地模型的代码评审多 Agent 协作平台

主 Agent 负责规划调度，多个专家子 Agent 并行评审，评审知识来自「向量 + 关键词」混合检索的知识库。全程不调用任何云端 API。

Python 3.10+ Qdrant + Elasticsearch llama.cpp 本地推理 FastAPI + SSE

1. 它能做什么

把一段代码（或 diff、架构图）交给它，它会像一支评审小组一样工作：

  • 主 Agent 先读代码，决定这次要派哪些专家、重点看什么；
  • 安全 / 性能 / 规范 / 测试 四位专家并行审查，需要查资料时自己调用技能（搜知识库、读文件、正则搜索）；
  • 最后主 Agent 汇总：合并重复项、校准严重度、输出总结。
角色模型运行方式
主 LLM（规划 / 评审 / 汇总）Qwen3.6-35B-A3B（MoE）llama-server，端口 8080
多模态（读架构图，可选）Qwen3-VL-8B-Instructllama-server，端口 8082
向量嵌入BAAI/bge-m3（可换 Qwen3-Embedding）Python 进程内加载

2. 快速开始

前置：Docker、Python 3.10+、llama.cpp（llama-server）、本地模型文件。

cd reviewhive

make infra          # ① 启动 Qdrant + Elasticsearch（docker compose）
make models-start   # ② 启动本地模型（8080 主模型 / 8082 多模态）
make install        # ③ 安装 Python 依赖
make ingest         # ④ 把种子知识库写入 Qdrant + ES
make serve          # ⑤ 启动，打开 http://localhost:9100
已经在跑 llama-server？第 ② 步可跳过——只要主模型监听在 127.0.0.1:8080 即可。用 reviewhive health 一键检查所有依赖是否就绪。

3. 页面怎么用

1
打开页面，看右上角的健康状态灯：LLM / Qdrant / ES 全绿表示就绪（VL 灰着没关系，不传图就用不到）。
2
左侧填入材料：粘贴代码或 diff；也可以点「附加架构图」传截图（走多模态）。新手直接点 载入示例代码。
3
点 开始评审。右侧时间线会实时直播：主 Agent 的调度计划 → 每个专家的技能调用 → 各自的产出。
4
几分钟后报告出现：顶部是总结与严重度统计，下面每条发现都带行号、证据代码、修改建议和引用的知识库编号。
想扩充知识库：reviewhive download-data 下载微软 CodeReviewer / CodeXGLZ 开源数据集，再 reviewhive ingest 入库即可。

4.1 总体架构

图 1 · 总体架构：接入层 → 编排层 → 能力层

4.2 一次评审是怎么跑起来的

主干是固定的五个阶段（保证一定能出报告），动态的部分发生在阶段内部：

阶段谁在做动态还是固定
① 受理流水线固定：解析代码、diff、图片，建立工作区
② 规划主 Agent动态：决定派哪些专家、本次关注点是什么
③ 检索RAG固定：按规划出的关注点预取知识库证据
④ 并行评审子 Agent动态：每位专家自主决定是否、何时调用技能
⑤ 汇总主 Agent动态：合并重复项、校准严重度、写总结

4.3 子 Agent 的「技能循环」

每位专家拿到任务后，按固定协议工作：每一轮只输出一个 JSON——要么「我要用技能」，要么「我审完了」。程序负责执行技能并把结果喂回去，直到专家给出结论。

图 2 · 技能循环：每位专家最多调用 4 轮技能，防止打转

4.4 知识库是怎么帮忙的（混合检索）

评审不能只靠模型「凭印象说」。系统维护了一个评审知识库，检索时走两条路再合并：

  • 向量路（Qdrant）：把问题变成向量找「意思相近」的条目——适合模糊描述，比如「线程不安全」；
  • 关键词路（Elasticsearch）：按词精确匹配——适合具体符号，比如 SimpleDateFormat；
  • 两路结果用 RRF 按名次融合（不需要给两边的分数做标定），再由 重排模型 逐条比对查询与候选，挑出最相关的几条交给 Agent。
图 3 · 混合检索管线：语义与精确互补，重排兜底质量

5.3 关键设计决策（为什么这么做）

Q：为什么用「混合编排」，而不是让主 Agent 完全自主规划？

本地量化模型的长程规划不稳定。主干固定保证「一定能出报告」，把自由度收敛到规划、技能调用、汇总三个点上——既有智能度，又可控、可复现、好调试。

Q：为什么自造 JSON 协议，不用模型原生的 function calling？

llama.cpp 的 tool calling 对不同模型/模板支持不一，量化后更容易输出坏格式。JSON 协议只依赖模型「输出合法 JSON」的能力，配合稳健的提取器（支持代码围栏、嵌入文本中的平衡括号扫描），对本地模型最可靠，也方便日志排查。

Q：嵌入模型为什么默认是 bge-m3？

接口做了可插拔：默认进程内加载本地已有的 bge-m3（多语言、1024 维、开箱即用）；下载 Qwen3-Embedding-8B 的 GGUF 后，改两行配置切到独立嵌入端点即可，检索层无需改动。

Q：检索为什么非要两路？

向量擅长「意思相近」，但对 SimpleDateFormat 这类精确符号召回弱；BM25 正好互补。RRF 只用名次融合，不需要给两边分数做标定，工程上最简单也最稳。

Q：某个组件挂了会怎样？

逐级降级：ES 挂了只剩向量路；检索全挂了 Agent 仍能凭模型能力评审；单个子 Agent 失败不影响其他专家；主模型不可用时也能返回带状态说明的报告。所有评审会话都落 SQLite，可回放。

Q：实时过程是怎么推到页面的？

评审在后台任务里跑，每个关键动作（阶段切换、技能调用、专家完成）写入会话事件队列，前端用 SSE（EventSource）订阅，逐条渲染成时间线。

Q：切片为什么做成可插拔的？

入库语料有三类（结构化种子、数据集、官方文档），未来还会加代码库级语料，切片方式不可能一套通吃。rag/chunking.py 定义统一的 Chunker 抽象与注册表：当前提供「结构优先（按标题成块）」与「定长滑窗」两种策略，由 settings.yaml 一行配置切换；以后要加代码 AST 切片、语义切片，继承 Chunker 实现 split() 再注册即可，入库与检索层零改动。

Q：链路追踪为什么选 Phoenix 且做成可选项？

调试多 Agent 系统最需要「一次评审到底发生了什么」的完整回放：Phoenix 单进程本地部署（Docker 一条命令），收 OTLP trace，能看到「会话 → 阶段 → 子 Agent → 每次 LLM 调用（prompt/补全/token/延迟）」的整棵树。做成可选是坚持全本地零负担的原则：LLM 调用走 openai SDK 被 OpenInference 自动埋点，编排链路在四个收口点手动加 span；开关关闭或依赖缺失时全部退化为 no-op，评审主流程完全不受影响。

6. 知识库与数据

知识库条目是统一的 JSON 结构，三类：review_example（评审样例）、vulnerability（漏洞模式）、best_practice（最佳实践）。示例：

{
  "source": "seed-java",
  "kind": "vulnerability",
  "language": "java",
  "title": "SQL 注入：字符串拼接构造 SQL",
  "content": "将外部输入直接拼接进 SQL 语句会导致注入……修复：参数化查询。",
  "code": "// 错误示例与正确写法对照"
}
  • 入库流程：条目 → 拼装「标题+内容+代码」→ bge-m3 向量化 → 同批写 Qdrant（语义）与 ES（全文）。
  • 官方文档语料：reviewhive fetch-docs 下载 OWASP 安全指南（16 篇）、阿里巴巴 Java 开发手册（p3c gitbook）、p3c 规则文档到 data/docs/，按目录名自动归类为 vulnerability / best_practice。
  • 切片策略：默认 heading（结构优先，按标题成块，单块 ≤1500 字），可在 settings.yaml 切换为 fixed_window，或按 chunking.py 注释三步扩展新策略。
  • 开源数据集：reviewhive download-data --limit 500 流式下载微软 CodeReviewer 与 CodeXGLZ 缺陷数据集并转成统一格式，再 reviewhive ingest。

7. 常见问题

问题处理
端口被占用改 config/settings.yaml 的 app.port（默认 9100）
健康检查有红灯先跑 reviewhive health；模型没起就 make models-start，存储没起就 make infra
第一次评审很慢首次要加载 bge-m3 / 重排模型（约十几秒），之后常驻内存
内存吃紧降低主模型 -c 上下文，或不启动多模态服务
想换主模型只要是 llama-server 的 OpenAI 兼容端点，改 models.llm.base_url 即可
